# Lyric Presenter module for the OWC multitrack player

This change adds a complete lyric presenter subsystem (10 phases, ~9300 lines across 68 files) to the existing WPF backtrack player. The module introduces a section-aware engine that syncs slides to audio playback via MIDI cues and timestamps, a Kestrel web server for per-musician stage displays over WebSocket, a WPF output window with double-buffered transitions and LibVLC video backgrounds, an operator control panel, PIN-authenticated remote control from phones/tablets, an NDI output pipeline (stub), and cloud sync preparation. The architecture follows the existing event-driven, code-behind pattern without a DI container.

**Watch for:** Default remote PIN "1234" ships enabled with no rate limiting on auth attempts (confirmed). Stage server binds 0.0.0.0 with no auth on `/stage` or `/stage/connections`, exposing song metadata to the LAN (confirmed). `BroadcastStageUpdate` in `PresenterIntegration` is a dead placeholder — stage clients never receive real-time updates via the integration path (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The PresenterEngine is a pure state machine that owns slide index, display state, and dual rendering (congregation strips chords, stage keeps them transposed). All output flows through events that the OutputWindow and StageDisplayServer subscribe to independently.

The stage server is an embedded Kestrel instance on port 5055 that multiplexes three concerns onto one HTTP process: musician WebSocket views with per-client capo/Nashville personalization, a remote-control WebSocket with PIN auth, and static HTML pages for both. Anyone on the network can see the current slides and connected-device list — no authentication required for the `/stage` paths.

The remote-control subsystem authenticates via a 4-digit default PIN ("1234") that produces an opaque hex token stored in `localStorage`. Token validity is unbounded — tokens never expire, and the auth endpoint has no rate limiting, so the PIN space can be enumerated in seconds.

Video backgrounds use LibVLCSharp with a shared `LibVLC` instance between the background service (looping motion videos) and the playback service (full-screen video items). `VideoBackgroundService` initializes LibVLC eagerly even when video backgrounds are never used.

NDI output is architecture-only: an `INdiOutput` interface in Core, a `StubNdiOutput` that discards frames, an `OutputCaptureService` that renders the WPF visual via `RenderTargetBitmap`, and an `NdiOutputService` that orchestrates the pipeline. No real NDI frames leave the machine.

Cloud sync is a stub `DesktopSyncService` implementing `ISyncService` with version-tracking and conflict-resolution logic but no network I/O and no persistence — restarting the app loses all sync state.

<details>
<summary>Issues (7)</summary>

1. **Default remote PIN "1234" enabled by default** — Change `RemoteEnabled` default to `false`, or generate a random PIN at first launch. A hardcoded weak PIN with no lockout on an open network port is an auth bypass.
2. **No rate limiting on `/remote/auth`** — Add exponential backoff or a lockout counter after N failed attempts; otherwise the 4-digit PIN is brute-forceable in <10 seconds.
3. **Stage server exposes song metadata without auth** — `/stage/connections` returns connected-client names/IPs to any requester. Either require an API key for that endpoint or remove it from the default route set.
4. **`BroadcastStageUpdate()` in PresenterIntegration is a no-op** — The method body is a comment. Wire `PresenterEngine.SlideChanged` to `StageDisplayServer.BroadcastSlideUpdate` or document that wiring is deferred to a future phase.
5. **Session tokens never expire** — `_validTokens` is a `HashSet<string>` with no TTL. Add an expiry (e.g., 24h) or clear tokens when the server restarts; currently `ClearAllTokens` exists but is never called.
6. **Remote WebSocket command injection via string interpolation** — `HandleRemoteMessage` builds a JSON string with `$"{{\"action\":\"{action}\"}}"` from an unescaped user string. If `action` contains a quote, the JSON becomes malformed. Use `JsonSerializer` to construct the command object.
7. **Video looping uses `input-repeat=65535`** — LibVLC may not honor this on all platforms/codecs. Consider handling `EndReached` and calling `Play` again for deterministic infinite loop.

<summary>Details</summary>

## Stage server network exposure

`StageDisplayServer.StartAsync` calls `options.ListenAnyIP(_port)`, binding Kestrel to all interfaces. No authentication is required to access `/stage`, `/stage/connections`, or the WebSocket endpoint `/ws/stage`. Any device on the local network can see the current lyrics, the list of connected musicians (names, IPs, capo settings), and receive real-time WebSocket pushes. `/stage/connections` is an information-disclosure endpoint that shouldn't be open by default — it leaks musician names, IPs, and configuration to unauthenticated requesters.

## Remote control auth weaknesses

The PIN is stored in plaintext in `PresenterSettings.RemotePin` (default "1234") and compared with a simple string equality in `RemoteCommandHandler.Authenticate`. The `/remote/auth` HTTP endpoint performs no rate limiting — a script can POST all 10,000 4-digit PINs in a few seconds. Once a valid PIN is found, the returned hex token never expires:

```csharp
lock (_tokenLock)
{
    _validTokens.Add(token); // no expiry, no cleanup
}
```

`ClearAllTokens()` exists but is never invoked — not on server restart, not on PIN change, not on a schedule.

`HandleRemoteMessage` in `StageDisplayServer` constructs a JSON string via string interpolation using the `action` field received from the WebSocket:

```csharp
commandJson = $"{{\"action\":\"{action}\"}}";
```

If `action` contains a double-quote or backslash, the produced JSON is malformed and `HandleCommand` returns "Invalid JSON". Not exploitable (the handler just fails), but fragile — `JsonSerializer.Serialize(new { action, data })` would be correct and no more expensive.

## Dead broadcast path in PresenterIntegration

`PresenterIntegration.BroadcastStageUpdate()` is called from `OnAudioEngineSectionChanged` and `OnSongLoaded`, but its body is:

```csharp
private void BroadcastStageUpdate()
{
    // Stage display broadcast happens through the StageDisplayServer
    // which is connected to PresenterEngine events in a real deployment.
    // This is a placeholder for the broadcast trigger.
}
```

No code subscribes `PresenterEngine.SlideChanged` to `StageDisplayServer.BroadcastSlideUpdate`. Stage WebSocket clients receive the initial state on connect (from `_lastBroadcastData`) but never receive subsequent updates through the integration path.

## NDI capture GC pressure

At 30fps the `OutputCaptureService` allocates a new `RenderTargetBitmap` and a new `byte[]` array every frame tick. On a complex visual tree this is ~8MB/s of short-lived allocations going straight to Gen0. A pooled buffer strategy (pre-allocate the byte array and reuse across frames) would eliminate the GC spikes (possible — needs profiling under real load).

## Video background loop fragility

The loop strategy uses `media.AddOption("input-repeat=65535")` — a finite repeat count. `VideoPlaybackService` handles `EndReached` to fire `PlaybackEnded` and supports auto-advance, but `VideoBackgroundService` has no `EndReached` handler. If the video eventually stops looping (unlikely in practice for short clips, but architecturally unclean), the background silently freezes with no recovery path.

## Cloud sync mutable state leak

`GetSyncStatusAsync()` returns `_trackedSongs.Values.ToList()`, giving callers mutable references to the internal `SyncInfo` objects. Tests exploit this to set `State = SyncState.Conflict` directly. Production consumers could corrupt internal state by mutating the returned items. Return cloned or immutable projections instead.

## Test coverage gaps

Not tested: the WebSocket server path (Kestrel startup, client connections, personalized broadcast), the `BroadcastSlideUpdate` delivery path, `OutputCaptureService` frame rendering (requires WPF runtime), `OutputWindow` transitions, the `PresenterIntegration` wiring (requires AudioEngine + full WPF), and the `HandleRemoteMessage` JSON-interpolation path.
