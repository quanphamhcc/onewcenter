This is the second pass on the 10-phase lyric presenter feature (~9500 lines across 69 files). All seven v1 issues have been addressed: RemoteEnabled defaults to false, rate limiting locks out after 5 failed PINs for 2 minutes, `/stage/connections` requires a valid token, `BroadcastStageUpdate` is wired with real data, tokens carry a 24h TTL cleared on server start, `HandleRemoteMessage` uses `JsonSerializer`, and `VideoBackgroundService.EndReached` restarts playback via `ThreadPool.QueueUserWorkItem`. ## High-level view

All v1 blocking issues are resolved. The remaining concerns are non-blocking: one missed endpoint in the auth-gate pattern, a GC pressure pattern that only matters when a real NDI sender is attached, and a mutable-reference leak in stub code.

`/remote/status` returns connected remote client names and IPs without requiring an auth token, mirroring the pattern that was fixed for `/stage/connections`. Low severity because the remote subsystem is disabled by default, but inconsistent with the neighboring endpoint's fix.

`OutputCaptureService` allocates a fresh `RenderTargetBitmap` and `byte[]` every frame tick. At 1920×1080×30fps this is ~248 MB/s of Gen0 allocations. Academic for the current stub NDI path, but will cause frame-dropping GC pauses when a real sender is plugged in.

## `/remote/status` information disclosure

The `/remote/status` GET endpoint returns connected remote client names, IPs, and connection timestamps with no auth check:

```csharp
_app.MapGet("/remote/status", () =>
{
    var remotes = _remoteClients.Values
        .Where(c => c.WebSocket.State == WebSocketState.Open)
        .Select(c => new { name = c.Name, ip = c.IP, connectedAt = c.ConnectedAt.ToString("o") })
        .ToArray();
    return Results.Json(new { connectedRemotes = remotes.Length, clients = remotes }, _jsonOptions);
});
```

The parallel endpoint `/stage/connections` was fixed in this pass to require a valid auth token — the same pattern should apply here. The HTTP endpoint is reachable on port 5055 regardless of the `RemoteEnabled` flag (only the WebSocket handshake checks that flag).

## NDI capture allocation pattern

`OutputCaptureService.CaptureFrame` on every timer tick:

```csharp
var renderBitmap = new RenderTargetBitmap(_width, _height, dpiX * scaleX, dpiY * scaleY, PixelFormats.Pbgra32);
renderBitmap.Render(_target);
byte[] pixels = new byte[stride * _height];
renderBitmap.CopyPixels(pixels, stride, 0);
```

`RenderTargetBitmap` is not reusable (WPF limitation), but the `byte[]` pixel buffer can be allocated once and reused across frames since `CopyPixels` overwrites the entire array. This halves the allocation pressure. For the bitmap itself, consider `WriteableBitmap` with `Lock`/`Unlock` to avoid per-frame GDI object creation on the real NDI path.

## v1 issue resolution verification

| v1 issue | Fix applied | Location |
|----------|------------|----------|
| Default PIN enabled | `RemoteEnabled` defaults to `false` | PresenterSettings.cs |
| No rate limiting | `MaxFailedAttempts = 5`, `LockoutDuration = 2 min` | RemoteCommandHandler.cs |
| `/stage/connections` unauthenticated | Token required via query or Authorization header | StageDisplayServer.cs |
| `BroadcastStageUpdate` dead code | Builds `StageDisplayData` from engine state, calls server | PresenterIntegration.cs |
| Tokens never expire | `TokenExpiry = 24h`; `ClearAllTokens` on `StartAsync` | RemoteCommandHandler.cs + StageDisplayServer.cs |
| JSON string interpolation | `JsonSerializer.Serialize(commandObj)` | StageDisplayServer.cs `HandleRemoteMessage` |
| Video loop fragility | `EndReached` → `ThreadPool.QueueUserWorkItem` → `Play` | VideoBackgroundService.cs |
