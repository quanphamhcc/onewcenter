# Implementation Plan — Service Order Persistence + Add/Edit/Delete

Derived from `.agents/tasks/service-persistence-bug.md` (authoritative report, sections A–F and the methods-to-change checklist). The data-loss bug is confirmed: `ServiceOrderManager.SaveAsync()` is defined (`WorshipPlayer.Core/Services/ServiceOrderManager.cs:76`) but has zero call sites, so added items live only in memory and vanish on restart.

## Grounding facts confirmed by exploration
- Solution: `WorshipBacktrackPlayer.sln` (repo root).
- UI exe project: `WorshipPlayer.UI/WorshipPlayer.UI.csproj` — `OutputType=WinExe`, `TargetFramework=net8.0-windows`, `AssemblyName=WorshipBacktrackPlayer`. Launched build output: `WorshipPlayer.UI/bin/Debug/net8.0-windows/WorshipBacktrackPlayer.exe` (or `bin/Release/...`).
- Test project: `WorshipPlayer.Tests/WorshipPlayer.Tests.csproj` — `net8.0` (NO WPF), xunit 2.6.6, references `WorshipPlayer.Core` only (Presenter is net8.0-windows and cannot be referenced; selected Presenter *service* .cs files are linked in). `ServiceOrderManager` lives in Core, so it is directly testable here.
- `ServiceOrderManager` API (do NOT rewrite): `CreateNew(name, date, serviceType?)`, `AddItem(ServiceItem)`, `RemoveItem(int)`, `MoveItem(from,to)`, `SaveAsync(string? filePath=null)` (auto-derives `{Date}_{SanitizeFileName(Name)}.json` under its base path; idempotent), `LoadAsync(path)`, `CurrentServiceOrder`, `CurrentItemIndex`.
- `ServiceItem` (`WorshipPlayer.Core/Models/ServiceOrder.cs`): `Type` (enum `ServiceItemType`: Song, Scripture, Announcement, Sermon, Video, Image, Prayer, Offering, AltarCall, Blank, Custom), `Title`, etc.
- Dialog: `WorshipPlayer.Presenter/Views/ServiceBuilder/AddServiceItemDialog.xaml` + `.cs`. `AddItem_Click` is currently a synchronous `void` handler; it calls `CreateNew` when `CurrentServiceOrder == null`, builds a `ServiceItem`, calls `AddItem`, raises `ItemAdded`, sets `DialogResult=true`, `Close()`. NOTE: the dialog's `ItemTypeComboBox` lists `Song/Scripture/Announcement/Sermon/Video/Blank/Custom`, while the code-behind `switch` maps `Song/Scripture/Announcement/Sermon/Video/Offering/Prayer` — a pre-existing mismatch; do NOT "fix" it unless an edit step requires reading the type back (see item 4).
- Operator window: `WorshipPlayer.Presenter/Views/OperatorWindow.xaml` (sidebar `ServiceOrderList` is an `ItemsControl` of plain strings, XAML ~217–227; `+ Add Item` → `NewService_Click`, `Load Service` → `LoadService_Click`) and `OperatorWindow.xaml.cs` (`NewService_Click` ~487; `RefreshServiceOrderList()` ~868 builds `"{icon} {Title}"` strings into `ObservableCollection<string> _serviceOrderItems`; field `_serviceOrderManager`; `ShowToolError(tool, msg)` ~1397; `SidebarColumn` width toggles 220/48 on collapse).
- Design system: `WorshipPlayer.Presenter/Themes/OwcDesignSystem.xaml` has keyed-only styles. Reuse the EXISTING `OwcServiceListBox` (`x:Key="OwcServiceListBox"`, TargetType ListBox, transparent bg, no border) — already used by MediaLibraryPanel, SongLibraryPanel, SettingsWindow, etc. Do NOT add an implicit (keyless) style — the report notes a prior `BorderBrush`/`UnsetValue` crash from that.
- Existing test conventions (e.g. `SongUsageServiceTests.cs`, `DefensiveLoadTests.cs`): class implements `IDisposable`, temp dir `Path.Combine(Path.GetTempPath(), $"...{Guid.NewGuid():N}")`, `Directory.CreateDirectory`, cleanup in `Dispose` with `Directory.Delete(dir, true)`, `[Fact]` async methods, `using Xunit;`.

# Implementation Plan

- [ ] 1. Add the persistence round-trip tests FIRST (they currently fail because save is never called from the UI, but they exercise Core directly which already works — so they will PASS once written; they lock in the behavior the fix must preserve).
      Create a new xunit test class covering, each with its own temp `ServiceOrders` dir cleaned up in `Dispose`: (a) `CreateNew` + `AddItem` + `SaveAsync()` writes a file, and `LoadAsync` on a brand-new `ServiceOrderManager` over the same dir returns the added item (survives "restart"); (b) after `RemoveItem(index)` + `SaveAsync()`, a fresh manager's reload no longer contains the removed item; (c) after mutating an item's `Title` and `Type` in `CurrentServiceOrder.Items[i]` + `SaveAsync()`, a fresh manager's reload reflects the new Title and Type. Derive the saved file path the same way the manager does — list `*.json` in the temp dir (there will be exactly one) rather than hard-coding the name.
      Files: `WorshipPlayer.Tests/ServiceOrderPersistenceTests.cs` (new).
      Verify: `dotnet test WorshipPlayer.Tests --nologo` → all green including the 3 new tests. (This proves the Core persistence contract the UI fix depends on BEFORE touching the UI.)

- [ ] 2. Core fix (A): persist after Add in the dialog. Make `AddServiceItemDialog.AddItem_Click` `async void`, wrap the add+save in try/catch, and after `ServiceOrderManager.AddItem(serviceItem);` call `await ServiceOrderManager.SaveAsync();`. Keep the existing `CreateNew("New Service", today)`-when-null behavior, the `ItemAdded` event raise, and `DialogResult = true; Close();` ordering (set `DialogResult`/`Close` after the await completes). On exception, show a message (do not crash the dialog) and still allow close.
      Files: `WorshipPlayer.Presenter/Views/ServiceBuilder/AddServiceItemDialog.xaml.cs`.
      Verify: `dotnet build WorshipBacktrackPlayer.sln --nologo` → 0 errors, no new warnings. (Behavior is runtime-verified at item 8.)

- [ ] 3. Persist helper (B): add `private async Task SaveServiceOrderAsync()` to `OperatorWindow` that returns early when `_serviceOrderManager?.CurrentServiceOrder == null`, else `await _serviceOrderManager.SaveAsync()` inside try/catch → `ShowToolError("Save Service", ex.Message)`. This is the single reuse point for edit/delete. Also, as defense-in-depth per report A alternative, in `NewService_Click`'s `ItemAdded` lambda keep `RefreshServiceOrderList()` and it is acceptable to additionally call `await SaveServiceOrderAsync()` — but the authoritative save remains item 2; do not double-prompt errors (guard so a failure surfaces once).
      Files: `WorshipPlayer.Presenter/Views/OperatorWindow.xaml.cs`.
      Verify: `dotnet build WorshipBacktrackPlayer.sln --nologo` → 0 errors, no new warnings.

- [ ] 4. Make the SERVICE ORDER sidebar selectable (C step 1) — bind to `ServiceItem` objects, not strings. In `OperatorWindow.xaml`, replace the `ItemsControl x:Name="ServiceOrderList"` (inside the existing `ScrollViewer`, ~217–227) with a `ListBox x:Name="ServiceOrderList"` using `Style="{StaticResource OwcServiceListBox}"` (keyed; reuse the existing style — do NOT introduce any implicit/keyless style, and do not set a bare `BorderBrush` that could resolve to `UnsetValue`). Give it an `ItemTemplate` whose `DataTemplate` has `d:DataType`/binds to `ServiceItem`, showing the icon + `Title` (a `TextBlock` with the icon prefix via a value converter OR two `TextBlock`s in a horizontal `StackPanel`: one for the icon, one bound to `Title`), preserving `Foreground="#F0F2F5"`, `FontSize="12"`, `Padding="10,5"`. In `OperatorWindow.xaml.cs`, change `RefreshServiceOrderList()` to populate a collection of `ServiceItem` (e.g. rebind `ServiceOrderList.ItemsSource` to `_engine?.CurrentServiceOrder?.Items` directly, or an `ObservableCollection<ServiceItem>` mirror); move the existing `Type`→icon `switch` into the template (via converter) or into a tiny view-model/display wrapper so the icon still shows. The selected index must map to `CurrentServiceOrder.Items[SelectedIndex]`. Keep `_serviceOrderItems` only if still referenced elsewhere; otherwise remove it cleanly.
      Files: `WorshipPlayer.Presenter/Views/OperatorWindow.xaml`, `WorshipPlayer.Presenter/Views/OperatorWindow.xaml.cs` (+ a small `IValueConverter` for Type→icon if that approach is chosen, in the Presenter project).
      Verify: `dotnet build WorshipBacktrackPlayer.sln --nologo` → 0 errors, no new warnings. Full runtime render check happens at item 8.

- [ ] 5. Extend `AddServiceItemDialog` for edit mode (C step 2). Add a public `ServiceItem? ItemToEdit { get; set; }` property and an `event EventHandler<ServiceItem>? ItemEdited`. When `ItemToEdit` is set (set by the caller before `ShowDialog`), on load pre-populate the combo boxes to reflect the item's current `Type` (and any other fields the dialog exposes). In `AddItem_Click`, branch: if `ItemToEdit != null`, mutate the existing item's `Type`/`Title` in place and raise `ItemEdited` INSTEAD of calling `CreateNew`/`AddItem`/`ItemAdded`; otherwise keep the existing add path from item 2. Optionally update the window Title/button text to "Edit" in edit mode. Do NOT call `SaveAsync` here for the edit branch — the operator window owns the save after `ItemEdited` (item 6), to keep one save path. (If pre-populating `Type` requires reading the combo back by the item's enum, reconcile only the entries you actually need; do not do an unrelated refactor of the Blank/Custom vs Offering/Prayer mismatch.)
      Files: `WorshipPlayer.Presenter/Views/ServiceBuilder/AddServiceItemDialog.xaml.cs` (and `.xaml` only if Title/button text binding is added).
      Verify: `dotnet build WorshipBacktrackPlayer.sln --nologo` → 0 errors, no new warnings.

- [ ] 6. Wire Edit affordance in `OperatorWindow` (C steps 2–3). Add an Edit trigger on the sidebar `ListBox`: `MouseDoubleClick` on `ServiceOrderList` AND a small "Edit" button or context-menu item (consistent dark OWC styling via existing keyed button styles). The handler: resolve the selected `ServiceItem` from `SelectedIndex`/`SelectedItem`; if none selected, no-op. Open `AddServiceItemDialog` with `Owner=this`, `ServiceOrderManager=_serviceOrderManager`, `ItemToEdit=<selected item>`; subscribe `ItemEdited` to, after confirm, `await SaveServiceOrderAsync()` then `RefreshServiceOrderList()`. Reuse the existing try/catch → `ShowToolError("Edit Service Item", ...)` pattern from `NewService_Click`.
      Files: `WorshipPlayer.Presenter/Views/OperatorWindow.xaml`, `WorshipPlayer.Presenter/Views/OperatorWindow.xaml.cs`.
      Verify: `dotnet build WorshipBacktrackPlayer.sln --nologo` → 0 errors, no new warnings. Runtime behavior verified at item 8.

- [ ] 7. Add Delete affordance + save (D). Add a "Remove" button or context-menu item near the sidebar (dark OWC styling, keyed styles). Handler: get `SelectedIndex`; if valid, call `_serviceOrderManager.RemoveItem(selectedIndex)` → `await SaveServiceOrderAsync()` → `RefreshServiceOrderList()`, inside try/catch → `ShowToolError("Remove Service Item", ...)`. (Reorder via `MoveItem` is OPTIONAL and only if low-risk — e.g. Up/Down buttons each calling `MoveItem` then `SaveServiceOrderAsync` + `RefreshServiceOrderList`; skip if it adds XAML complexity or risk.) Startup reload (E) needs NO code change — note that `PresenterIntegration.AutoLoadMostRecentServiceOrderAsync` already reloads the newest `ServiceOrders/*.json`; confirm it still works at runtime (item 8). No-current-service case (F) is already handled by `CreateNew` in the dialog; leave the always-"New Service" name as-is (optional naming polish is explicitly out of scope for this plan).
      Files: `WorshipPlayer.Presenter/Views/OperatorWindow.xaml`, `WorshipPlayer.Presenter/Views/OperatorWindow.xaml.cs`.
      Verify: `dotnet build WorshipBacktrackPlayer.sln --nologo` → 0 errors, no new warnings; then `dotnet test WorshipPlayer.Tests --nologo` → all green (447 + new).

- [ ] 8. Runtime launch + end-to-end manual verification (covers A–F behavior). Build, then launch the UI exe and exercise the flow.
      Files: none (verification only).
      Verify: run `WorshipPlayer.UI/bin/Debug/net8.0-windows/WorshipBacktrackPlayer.exe` (match the configuration you built). Confirm: (1) app starts with NO `(DependencyProperty.UnsetValue) is not a valid value for property 'BorderBrush'` crash and no XAML load exception; (2) Services tab / SERVICE ORDER sidebar renders as a selectable list; (3) `+ Add Item` adds an item that persists after fully closing and reopening the app (the data-loss bug is fixed — a `ServiceOrders/{yyyy-MM-dd}_New Service.json` file is written); (4) double-click / Edit changes an item's type/title and the change survives restart; (5) Remove deletes the selected item and the deletion survives restart.
