# Settings stores (AppSettings + PresenterSettings) migrated to shared SQLite app.db

Phase 4 does two things in sequence. First it collapses the two independent `presenter-settings.json` writers into a single `PresenterSettingsService` (Core), killing the dead static writer in `MainWindow` and routing the live `PresenterIntegration` save callback through the service. Then it repoints both settings stores — `SettingsService` for `AppSettings` and the new `PresenterSettingsService` for `PresenterSettings` — at the shared `app.db` through the existing `AppDatabase` helper, each as a single-row `(Id=1, DataJson TEXT)` table with a defensive one-time legacy-JSON import. The public API (`Settings`/`LoadAsync`/`SaveAsync`) is unchanged and both construction sites in `MainWindow` now pass the `app.db` path. No EF, no second db helper, `bible.db` untouched, and nothing in service-orders or songs was touched.

Watch for: the two stores diverge intentionally on auto-create (AppSettings writes a defaults row when empty, PresenterSettings does not) — this matches prior behavior and is covered by tests (confirmed). Stale comment in `PresenterIntegration.cs:426` calls the service "file-backed" when it is now DB-backed — cosmetic only (confirmed).

**Verdict**: APPROVED

## High-level view

The consolidation is clean: `PresenterIntegration.SavePresenterSettings` now sets `_presenterSettingsService.Settings = settings` and calls `SaveAsync()` while still invoking `ApplyDisplaySettings`, and the `OperatorWindow` save-callback wiring is unchanged. The dead `MainWindow.SavePresenterSettings`/`LoadPresenterSettings`/`GetPresenterSettingsPath` are gone from the worktree.

Both stores share `app.db` via `new AppDatabase(path)` with `CREATE TABLE IF NOT EXISTS ... CHECK (Id = 1)` and a single-row upsert. There is no second db helper, no EF, and the `.csproj` files and `bible.db` are untouched by the diff.

Legacy JSON import is one-time, non-duplicating, and swallows all exceptions: a missing or malformed `settings.json` / `presenter-settings.json` falls back to defaults and never throws. SettingsService additionally writes a defaults row when neither a row nor a legacy file exists, preserving its historical auto-create behavior; PresenterSettings deliberately does not.

Additive E5/J4 fields and the `AppSettings` enums round-trip through the JSON column (enums as string names), verified both by reload assertions and by reading the `DataJson` column directly.

### Single presenter-settings writer

The known double-writer trap is resolved. `PresenterIntegration.SavePresenterSettings` dropped its inline `JsonSerializer.Serialize` + `File.WriteAllText` block and now delegates to the injected service, keeping `ApplyDisplaySettings(settings)` and the `OperatorWindow.Initialize(..., SavePresenterSettings)` callback intact. A worktree grep confirms the dead `MainWindow` static writer and its loader/path helpers are deleted (remaining matches are in the un-migrated main checkout, out of scope). The ctor param ordering (`PresenterSettings` then `PresenterSettingsService` then `SongManager`) matches the `MainWindow` call site.

The save path runs `SaveAsync().GetAwaiter().GetResult()` synchronously from the UI callback. On a fire-after-change path with no captured SynchronizationContext this is fine; the FEAT-001 note flagged it and it remains self-contained.

### Shared app.db backing, single-row DataJson

Both services build `new AppDatabase(path)` and own their own `CREATE TABLE IF NOT EXISTS <Store> (Id INTEGER PRIMARY KEY CHECK (Id = 1), DataJson TEXT NOT NULL)`, which keeps schema-init order-independent across stores on the one `app.db`. Reads are `SELECT DataJson WHERE Id = 1`; writes are `INSERT ... ON CONFLICT(Id) DO UPDATE`. The `_initialized` guard runs schema-init + import once per process. No per-field column promotion, matching the plan.

### Legacy import and the deliberate auto-create asymmetry

`ImportLegacyJsonIfNeededAsync` in both services is wrapped in a catch-all, checks the sibling file exists, guards against an existing row, and writes once. SettingsService then writes a defaults row when the store is still empty (preserving the old `LoadAsync` auto-write); PresenterSettingsService intentionally skips that, since presenter settings never auto-created a file. This behavioral difference is explicit in both the code comments and the tests (`LoadAsync_NoRow_YieldsDefaults_AndDoesNotCreateRow` reopens a fresh service and still sees defaults, proving no row was written).

### Test coverage

`SettingsServiceTests` (5) and `PresenterSettingsServiceTests` (6) both use a temp `app.db` with `SqliteConnection.ClearAllPools()` teardown. Coverage: defaults with no row/file, save→reload through a fresh instance, additive E5/J4 and NDI/stage/remote/shortcut survival, single-save-path identity, one-time import with second-instance-no-duplicate, and malformed-legacy → defaults-no-throw. The enum test reads the `DataJson` column directly and asserts `MultiOutput`/`After2Bars` are stored as string names. Full suite: 601/601 pass.

Not tested: the synchronous `GetAwaiter().GetResult()` save path from the real UI callback (not unit-testable here); concurrent access to `app.db` across stores (out of scope for this phase).
