# OWC command center redesign for OperatorWindow

The OperatorWindow gets a full visual overhaul from a three-column utility layout to a top-down "command center" structure matching the OWC Design Identity. The layout now stacks: hero live previews at the top, a header bar with search/NDI/theme controls, a collapsible sidebar + slide grid in the middle, and a full-width transport bar at the bottom. New behavioral features include a zoom slider controlling thumbnail size, an edit mode that suppresses fire-on-click, number-key jump shortcuts, and sidebar collapse. A new resource dictionary (`OwcDesignSystem.xaml`) externalizes design tokens.

Watch for: Edit mode click handler is a no-op that re-renders without tracking selection (confirmed). No event unsubscription or cleanup on window close — engine event handlers will keep the window alive via delegate references (confirmed). Button hover trigger in the design system sets the same color as the resting state, producing no visible feedback (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The public API surface is unchanged — `Initialize` overloads, `UpdateBacktrackStatus`, and `UpdateConnectedDevices` retain their signatures — so integration-layer callers won't break.

The slide grid gains zoom via a WrapPanel whose children are sized from the slider value. Rendering is purely imperative (clear-and-rebuild on every slide change), creating allocation pressure on rapid navigation through large slide sets. The edit mode toggle introduces a `_isEditMode` flag but the corresponding click handler in edit mode doesn't actually select anything — it calls `RefreshSlideThumbnails()` without tracking which slide was clicked.

Event subscription happens in `Initialize` with no corresponding unsubscription. The engine holds references to the window's handlers, preventing garbage collection if the engine outlives the window. The old code had the same pattern, but since this is a rewrite it should be fixed.

The keyboard shortcut TextBox guard is new and correct for the text input case, but `B` fires `GoBlack` unconditionally when any non-TextBox element has focus (likely concern when the search placeholder becomes a real input).

## Edit mode selection gap

The `_isEditMode` flag toggles correctly and the button visual updates, but the behavior when a thumbnail is clicked in edit mode does nothing useful:

```csharp
border.MouseLeftButtonDown += (s, ev) =>
{
    if (_isEditMode)
    {
        // In edit mode, just select (highlight) without firing live
        RefreshSlideThumbnails();
    }
    else
    {
        _engine?.GoToSlide(capturedIndex);
    }
};
```

`RefreshSlideThumbnails()` highlights whatever `_engine.CurrentSlideIndex` is — it has no concept of a separate "selected but not live" index. The code needs a `_selectedSlideIndex` field, set to `capturedIndex` in the edit branch, and the rendering logic needs to distinguish between "active/live" (cyan glow) and "selected/editing" (different indicator, perhaps a dashed border or dimmer highlight).

## Event lifecycle and resource leaks

Six engine events and one theme event are subscribed in `Initialize`:

```
_engine.SlideChanged += OnSlideChanged;
_engine.ItemChanged += OnItemChanged;
_engine.DisplayStateChanged += OnDisplayStateChanged;
_engine.PitchShiftChanged += OnPitchShiftChanged;
_engine.TempoChanged += OnTempoChanged;
_engine.SongLoaded += OnSongLoaded;
_themeManager.ThemeChanged += OnThemeChanged;
```

There is no `OnClosed` override, no `Dispose`, no unsubscription path. If the window is closed while the engine continues running (common during development or if the operator window is re-opened), the engine's delegate list holds a reference to the closed window, preventing GC.

## Slide grid rebuild cost

`RefreshSlideThumbnails()` is called on every `SlideChanged` event (via `OnSlideChanged`), which fires on every Prev/Next click. The method clears all WrapPanel children and recreates them from scratch. Each thumbnail is a Border containing a Grid containing three TextBlocks — so for a 30-slide song, that's 120+ WPF elements destroyed and recreated per navigation step.

A more efficient pattern: keep the children in place and update only the `BorderBrush`/`BorderThickness` of the previously-active and newly-active borders. Only rebuild fully when the slide set changes (item change, zoom change).

## Button hover trigger produces no visible change

```xml
<Style.Triggers>
    <Trigger Property="IsMouseOver" Value="True">
        <Setter Property="Background" Value="{StaticResource OwcSurfaceBrush}" />
    </Trigger>
</Style.Triggers>
```

The default `Background` is already `OwcSurfaceBrush`, so this trigger changes nothing. Every button using `OwcButtonBase` (which includes `OwcTransportButton`, `OwcTransportButtonDark`, `OwcAccentButton`, `OwcLiveButton` via `BasedOn`) inherits a non-functional hover state. The trigger should target a lighter value — perhaps a dedicated `OwcSurfaceHoverBrush` at `#2F3544` or similar.

## Stage CONNECTED indicator is hardcoded

The Stage preview box renders a green dot and "CONNECTED" text unconditionally in XAML. No code-behind method updates this indicator. If the stage display WebSocket server is running but has zero connected clients, the operator still sees green. The `UpdateConnectedDevices` method updates a count in the header bar but doesn't touch the stage preview indicator — these are logically related but disconnected in the UI.
