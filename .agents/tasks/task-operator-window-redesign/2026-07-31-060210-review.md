# OWC command center redesign for OperatorWindow (v2)

The OperatorWindow has been rewritten from a three-column utility layout to a top-down command center matching the OWC Design Identity. All six issues from the first review pass are addressed: edit mode now tracks `_selectedSlideIndex` with a distinct `#0088AA` border, `OnClosed` unsubscribes all engine/theme/NDI/capture events, the button hover trigger uses a dedicated `OwcSurfaceHoverBrush` (#2F3544), `OnSlideChanged` calls the lightweight `UpdateSlideThumbnailHighlights()` instead of full rebuild, the keyboard guard expands to `TextBoxBase || ComboBox`, and the stage CONNECTED indicator is dynamically driven by `UpdateStageConnectionIndicator()`.

Watch for: Brush allocations inside the highlight loop recreate objects on every navigation (possible, non-blocking). Accent/live button styles in the design system inherit a hover trigger that would regress colored backgrounds to grey if the styles are ever applied (possible, non-blocking). Number-key shortcuts fire `GoToSlide` without bounds checking against the actual slide count (likely, non-blocking).

**Verdict**: APPROVED

## High-level view

The public API surface is unchanged — `Initialize` overloads, `UpdateBacktrackStatus`, and `UpdateConnectedDevices` retain their signatures.

The slide grid now uses a two-tier update strategy: `RefreshSlideThumbnails()` for structural changes (item switch, zoom), `UpdateSlideThumbnailHighlights()` for navigation. The highlight method allocates a new `SolidColorBrush` per border per navigation step and parses `#0088AA` via `ColorConverter` inside the loop — minor GC pressure that could be eliminated with static frozen brush fields.

The design system defines `OwcAccentButton` and `OwcLiveButton` styles that inherit the base hover trigger, which sets background to `OwcSurfaceHoverBrush`. Applying these styles to colored buttons would regress them to grey on hover. The current XAML avoids this by using inline properties, so the issue is latent — but the styles are traps for future use.

Number-key shortcuts (D1–D9) call `_engine?.GoToSlide(n)` unconditionally. If the current item has fewer than 9 slides, the behavior depends entirely on the engine's internal bounds checking with no client-side guard.

## Brush allocation pattern in UpdateSlideThumbnailHighlights

The method allocates `SolidColorBrush` instances for all borders on every call:

```csharp
border.BorderBrush = isActive
    ? new SolidColorBrush(AccentCyan)
    : isSelected
        ? new SolidColorBrush((Color)ColorConverter.ConvertFromString("#0088AA"))
        : new SolidColorBrush(BorderColor);
```

For a 30-slide song navigated rapidly (holding the right arrow key), this produces 30 brush allocations per frame. The `ColorConverter.ConvertFromString` call inside the loop adds string parsing overhead on every iteration.

Fix by hoisting to static frozen brushes:

```csharp
private static readonly Color EditSelectedColor = (Color)ColorConverter.ConvertFromString("#0088AA");
private static readonly SolidColorBrush AccentBrush = new(AccentCyan);
private static readonly SolidColorBrush EditSelectedBrush = new(EditSelectedColor);
private static readonly SolidColorBrush DefaultBorderBrush = new(BorderColor);
```

Not a functional bug, but a missed optimization given the stated goal of the method (avoiding the rebuild cost).

## Number-key out-of-bounds

The keyboard handler dispatches without bounds checking:

```csharp
case Key.D5: _engine?.GoToSlide(4); e.Handled = true; break;
```

If `_engine.TotalSlides` is 3, this sends index 4 to the engine. The operator window provides no guard or user feedback. Adding `if (4 < _engine.TotalSlides)` makes the contract explicit and avoids relying on engine-internal clamping.
