# Implementation Plan — Service Name + Service Date (US format) on new-service creation

## Goal
When the user creates a new service, let them set a **Service name** and a **Service date with time** in **US format** (`MM/DD/YYYY hh:mm tt`, e.g. `10/18/2026 08:00 AM`), matching the user's screenshot. Today a new `ServiceOrder` is auto-created with the hardcoded name `"New Service"` and `DateTime.Today` with no UI (confirmed in `AddServiceItemDialog.AddItem_Click`, which calls `ServiceOrderManager.CreateNew("New Service", today)` when `CurrentServiceOrder == null`). Backward compatibility is mandatory: existing date-only `ServiceOrders/*.json` must still load.

## Design decisions (grounded in the code I read)
- **Model (verified `WorshipPlayer.Core/Models/ServiceOrder.cs`): keep `Date` as a `string`.** It is `[JsonPropertyName("date")]` and existing files (`2026-08-03_Sunday Morning.json`, `TheBlessing Service.json`) store date-only like `"2026-08-03"`. Changing its type would break those files and `GetDefaultFilePath` (which builds the filename from `order.Date`). **Decision:** keep `Date` exactly as-is (date-only string, stays `yyyy-MM-dd` so the derived filename and existing `OrderByDescending(o => o.Date)` sort are unchanged) and **add a new nullable `DateTime? StartTime`** property `[JsonPropertyName("startTime")]` holding the optional time-of-day (and date). Rationale: nullable + the manager's existing `DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull` means date-only files simply deserialize `StartTime = null` and nothing is written for services without a time — fully backward compatible, no converter needed. The UI formats `Date` (+ `StartTime` when present) into the US display string; it does not need a new string field.
- **US formatting independent of OS locale:** everywhere the new UI parses/formats a date or time, use an explicit `CultureInfo` for en-US (`new CultureInfo("en-US")` / `CultureInfo.GetCultureInfo("en-US")`) and the `DatePicker.SelectedDateFormat`/custom format strings, so a Vietnamese Windows locale still shows `MM/DD/YYYY` and `AM/PM`. Verified need: the app runs on a `vi-VN` machine.
- **New dialog is its own `Window` that MERGES `OwcDesignSystem.xaml`** (same pattern as `AddServiceItemDialog.xaml`, which merges it via `pack://application:,,,/WorshipPlayer.Presenter;component/Themes/OwcDesignSystem.xaml`). This lets it safely use the keyed styles `OwcTextBox`, `OwcDarkComboBox`, `OwcButtonBase`, `OwcAccentButton` and the `Owc*Brush` resources (all confirmed present in `OwcDesignSystem.xaml`). We do **not** touch `OperatorWindow.xaml` resources.
- **Create-time wiring without StaticResource in OperatorWindow:** the create path is reached in two places — `OperatorWindow.NewService_Click` (the "+ Add Item" button, confirmed `Click="NewService_Click"` in `OperatorWindow.xaml`) and `AddServiceItemDialog.AddItem_Click` (fallback `CreateNew` when no order loaded). We show the new `ServiceInfoDialog` from the **code-behind** `NewService_Click` only when `_serviceOrderManager.CurrentServiceOrder == null`, before opening `AddServiceItemDialog`. All dialog markup/styles live in `ServiceInfoDialog.xaml`; `OperatorWindow.xaml` gets **zero** new `{StaticResource}` references (no XAML change to OperatorWindow at all — only code-behind). This honors the two prior-crash lessons.
- **Edit-existing path (low-risk plus):** add an "Edit Service" button to the sidebar `StackPanel` in `OperatorWindow.xaml` using the **same hardcoded inline brush style** as the sibling buttons (`Background="#252A36" Foreground="#F0F2F5" BorderBrush="Transparent"`), wired to a new `EditService_Click`. No StaticResource. It opens the same `ServiceInfoDialog` pre-filled from `CurrentServiceOrder` and saves via the existing `SaveServiceOrderAsync()`.
- **Build/test commands (verified working during exploration):**
  - Core+Tests build: `dotnet build WorshipPlayer.Tests/WorshipPlayer.Tests.csproj -c Debug` → `Build succeeded. 0 Error(s)`.
  - Presenter (WPF) build: `dotnet build WorshipPlayer.Presenter/WorshipPlayer.Presenter.csproj -c Debug` → `Build succeeded. 0 Error(s)` (2 pre-existing unrelated CS0414 warnings).
  - Tests run: `dotnet test WorshipPlayer.Tests/WorshipPlayer.Tests.csproj -c Debug`.
  - Windows launch (CRITICAL, must verify manually): `dotnet run --project WorshipPlayer.Presenter -c Debug` (or launch the built exe) and confirm the Operator window opens without the `Provide value on 'System.Windows.StaticResourceExtension'` crash, that "+ Add Item" on an empty service shows the new dialog, and that the new dialog's inputs render dark/readable.

## Notes / assumptions
- Time is optional. If the user leaves it blank, `StartTime` stays `null` and nothing time-related is written (file stays date-only) — matches the "+ Add time" optional affordance in the screenshot.
- `Date` stays `yyyy-MM-dd` in storage so `GetDefaultFilePath` filenames and the `OrderByDescending(o => o.Date)` sort in `LoadAllAsync` keep working; US `MM/DD/YYYY` is a display/entry concern handled by `ServiceDateFormatter`.
- Do not touch chord rendering, `LoadStandaloneSong`, F2/F3 `LoadSong`, or the existing ComboBox theme. No implicit keyless styles. No `{StaticResource}` added to `OperatorWindow.xaml`.
