# Implementation Plan — Slides editors: reliable touch + mouse input

## Goal

Make the Slides editor modal windows work reliably with BOTH touch and mouse while the audience `OutputWindow` is live (Topmost). The user reports Close/Cancel being very hard to activate, especially by touch. A first fix already landed (commit a0baaed) making `SlideServiceItemEditorWindow` `Topmost=true` + `Activate()` on load, fixing the MOUSE case for that one window. This plan finishes the job for the other Slides modals and for TOUCH.

## Design decisions (made here, grounded in the code I read)

- **Topmost strategy = per-dialog Topmost + Activate on load (the lower-risk option already started).**
  Rationale: the already-shipped fix for `SlideServiceItemEditorWindow` uses exactly this. Extending the same pattern to `SlideEditorWindow` and `ListPickerDialog` is consistent, local, and cannot blank or move the live output. The alternative — temporarily clearing `OutputWindow.Topmost` while a modal is open — would have to hook every modal open site, restore on every exit path including exceptions, and risks the live screen falling behind other windows. I read `OutputWindow.xaml.cs`: `Topmost` is set in `PlaceOnDisplay` (line 161), `GoFullScreen` (default true), and cleared only in `ExitFullScreen`. Touching that global state from the editor flow is higher blast-radius for no extra benefit, so we reject it. Each Slides modal owns its own `Topmost`.

- **Touch root cause is NOT a swallow inside the Slides windows.** I grepped the three Slides files for `IsManipulationEnabled`, `PanningMode`, `StylusDown`, `TouchDown`, `ManipulationStarting`, `StylusSystemGesture` — none exist there. The only `PanningMode`/`IsManipulationEnabled` usages are in `OperatorWindow.xaml` (the service-order list and slide-sections scroller), which are OUT OF SCOPE and must be left alone per the task constraints. Therefore the dominant touch failure is the same z-order problem the mouse fix addressed (a Topmost full-screen `OutputWindow` intercepting input to a non-Topmost modal), compounded by small hit targets. Making every Slides modal Topmost + active, plus enlarging the short buttons, is the fix. Remaining touch->mouse promotion behavior that cannot be proven by reading XAML is called out below as "needs verification during implementation."

- **Hit-target sizing via a dedicated keyed touch style, not inline hacks and not a global Button style.** `OwcDesignSystem.xaml` deliberately has NO implicit `Button` style (an explicit comment warns a global one caused a `DependencyProperty.UnsetValue` crash). So we add ONE new keyed style `OwcTouchButton` (BasedOn `OwcButtonBase`) with `MinHeight=36` and we add `MinHeight` to the existing `OwcCompactButton`. We do NOT change `OwcButtonBase` itself (it is used app-wide). The short offenders (rename `✎` MinWidth=30, rename `Cancel` MinWidth=60, the `OK` button, compact chips, and the `+`/`✕` icon buttons that are fixed Height=28) get a MinHeight bump so effective touch height reaches 36px. This keeps keyed OWC styles and the dark theme intact.

- **Scope discipline.** Only the three Slides editor windows and the two keyed styles change. `OperatorWindow.xaml(.cs)` is touched ONLY at the `ListPickerDialog`/`SlideEditorWindow` open sites if needed (none required — those windows set their own `Topmost`), and if any host code is added it uses inline brushes only (OperatorWindow uses no ResourceDictionary/StaticResource). No model, live-link, or unrelated-window changes. No global touch disable. No DiagLog / file logging.

## Notes / gaps (reasonable assumptions made)

- No automated test can assert touch z-order or first-tap activation in this repo; the plan therefore leans on runtime manual verification on the touchscreen+mouse rig, as the task requires. The coder must actually run the app Live and exercise touch, not infer from XAML.
- Exact MinHeight (34–36) and the `+`/`✕` icon Height (32) are chosen to clear a ~32–40px touch target while fitting the existing compact header/footer rows; if any value visibly breaks the reference dark layout, prefer the smallest value in that range that still reaches first-tap reliability, and keep padding symmetric.
- `OwcTouchButton` is introduced rather than overloading `OwcCompactButton` so that primary header/footer buttons (Close/Cancel) can be enlarged independently of the smaller inline chips.
